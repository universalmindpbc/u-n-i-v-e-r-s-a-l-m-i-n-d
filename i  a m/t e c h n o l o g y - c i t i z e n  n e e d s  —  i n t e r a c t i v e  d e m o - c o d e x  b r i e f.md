# Citizen Needs — Inference Engine | Codex Brief

## Codex Creative + Interaction Brief

This page is the official creative and interaction brief for building the **Citizen Needs — Inference Engine** component inside the **I Am** portal.

The tone should feel like **Apple meets Google DeepMind meets Garvan Institute of Medical Research**: elegant, precise, scientifically literate, visually memorable, and calm.

This component should help a broad audience understand how Universal Mind interprets human check-ins while also signalling a deeper technical roadmap to specialist partners.

---

# Purpose

The **Citizen Needs — Inference Engine** radar is not a dashboard.

It is an interactive explanation of how Universal Mind thinks about human needs, emotional states, physiological signals, clinical risk, and future biological inference.

The objective is that a visitor understands the model in approximately **10–15 seconds**, without being forced to read a wall of text.

It should feel more like a premium interactive exhibit than a scientific graph.

---

# Creative Inspiration

The radar is inspired by the meeting point of three visual / conceptual systems:

1. **Maslow-style human needs architecture**
    
    A structured model of what people need to feel safe, connected, regulated, understood, and supported.
    
2. **Attention / safety radar**
    
    A real-time visual field showing levels of alertness, threat, arousal, safety, attention, and recovery.
    
3. **Clinical survey / scatterplot logic**
    
    The way clinicians interpret survey responses across multiple domains rather than relying on one single score.
    

The result should feel like a distilled Universal Mind model, not a literal copy of any of those systems.

# Design Philosophy

The component should progressively reveal information.

Do not show every label at once.

The default state should be beautiful, calm and mysterious.

The user should discover the model by hovering, clicking or tapping.

Avoid:

- dashboards
- gaming interfaces
- startup SaaS charts
- heavy scientific infographics
- fake diagnostic precision
- overwhelming labels

Aim for:

- Apple-level restraint
- DeepMind-level intelligence
- Garvan-level scientific discipline
- Vogue-level visual confidence

# GPT-Powered Check-In Inference

This component must use a GPT-powered inference call as the core interpretation method.

Do not use a local keyword dictionary as the main inference layer.

Do not build a “dumb” prototype where fixed words map mechanically to radar categories.

The first implementation should establish the correct seed architecture:

**Citizen self-report → GPT language inference → Citizen Needs radar highlight**

Even if the first prompt is simple, the architecture should begin with a real GPT model interpreting the citizen’s language.

---

## Model Direction

Preferred model for the first version:

**GPT-5.5**

When available and approved for use, migrate the inference call to:

**GPT-5.6**

The model name should be configurable in one obvious place so future upgrades do not require rebuilding the component.

---

## What The GPT Call Does

When a citizen enters an **“I am…”** check-in, the GPT model should analyse the text and map it to exactly four relevant highlights from the existing Citizen Needs radar.

Example input:

> I am happy, connected and grounded.

Example output:

```json
{
  "highlights": [
    "Joy",
    "Connection",
    "Calm",
    "Psychological Safety"
  ],
  "interpretation_type": "language_theme_mapping",
  "clinical_status": "not_a_diagnosis"
}
```

The radar then animates these four regions.

The wheel may spin, settle, then illuminate the selected factors with elegant bloom / glow animation.

The interaction should feel like the citizen’s language is being gently understood by the system.

---

## Output Rules

The GPT model must return structured JSON only.

The JSON should include:

- exactly four radar highlight labels
- optional confidence language if useful
- no diagnosis
- no clinical score
- no long prose
- no therapeutic advice
- no claim of certainty

The returned labels must match existing radar labels so the animation can reliably highlight the correct regions.

---

## Interpretation Rules

The GPT call is performing language-theme interpretation.

It is not diagnosing the citizen.

It is not producing a clinical assessment.

It is not claiming to know the citizen’s true state.

The interface should communicate:

> “These are the themes the model is currently exploring.”

not:

> “This is what is wrong with you.”

---

## Privacy + Safety Rules

The user’s “I am…” text should not be shown publicly on the globe without explicit consent.

For the first prototype, the check-in may visually become an anonymous glowing node or highlight sequence, but it should not broadcast the exact raw text as though it is public social media.

The experience should feel private, respectful and consent-led.

---

## Technical Architecture Direction

The public browser should not call GPT directly with a visible API key.

Use a private server-side API route or equivalent secure function.

The browser sends the “I am…” text to the private route.

The private route sends the request to GPT.

GPT returns structured JSON.

The browser receives only the safe structured result and animates the radar.

---

## Fallback Behaviour

If the GPT call fails, do not fake an inference.

Show a graceful message such as:

> We could not interpret this check-in yet. Please try again.

or

> The inference engine is unavailable for this prototype.

Do not silently replace GPT with a keyword dictionary unless Ben explicitly asks for a fallback demo mode.
